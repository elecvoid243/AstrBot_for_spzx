# Agent Teams 改进建议报告

- 日期：2026-09-14
- 性质：外部评审建议（非设计方案；每条建议落地前需按惯例出独立 design spec）
- 评审基线：[2026-09-05-agent-teams-design.md](specs/2026-09-05-agent-teams-design.md)（已落地）+ Refinements 1-3；Phase 1（条件分支）、Phase 2（Human Input）、Phase 3（循环边）、Subworkflow、模板库均为设计评审中
- 评审方法：通读 `agent_team_service.py` / `agent_team_run_service.py` / `agent_team_dag.py` / `agent_team_ports.py` / `core/agent_team_tools.py` 实现，并与 DeepSeek Harness（dsh）的 Agent Teams 实现做了对照分析

## 1. 总体评价

底座是干净的：`TeamPorts` 注入缝让 runner 可脚本化测试；逐转换落盘使重启恢复有据可依；per-umo 工具注册表保证了协作工具不泄漏到普通回合；星型拓扑和 create-only 成员约束在 v1 刻意收敛了复杂度，这些都是正确的取舍。

当前的主要短板集中在三处：**执行引擎的波次屏障与墙钟超时**（吞吐与误杀）、**digest 作为全链路信息瓶颈**（协调者基于每成员 500 字符做决策）、**结构化输出契约的可靠性**（条件分支/循环边的地基）。下文按优先级展开。

## 2. P0 —— 局部改动、立竿见影

### 2.1 事件驱动调度替换波次屏障

**现状**：`agent_team_run_service.py` `_run_loop` 每轮计算就绪集 → 截取前 `max_parallel` 个 → `asyncio.gather` 等待**整批完成** → 再算下一波。同波一个慢节点（成员在跑长工具调用）会拖住同波快节点的全部后继，`max_parallel=5` 时利用率损失最明显。

**建议**：改为 per-node `asyncio.Task` + `asyncio.Semaphore(max_parallel)` + 每节点仅等待自己的直接前驱完成事件。拓扑序由前驱事件链天然保证，`agent_team_dag.py` 的校验逻辑不变，`TeamPorts` 与落盘时序不变——纯 runner 内部重构。

**成本/风险**：低。恢复路径（从 `node_states` 重建）需同步改为"重建未完成节点的任务图"，注意 `pause` 语义从"波间暂停"变为"信号量排空后暂停"。

### 2.2 空闲超时替代墙钟超时

**现状**：`reply_timeout`（600s）是固定墙钟时限。成员正在活跃地流式输出或连续调用工具时也可能被判节点失败；这正是默认值从 collab 的 180s 翻倍的根因——不是成员真的需要 600s，而是怕误杀。

**建议**：`collect` 已订阅增量事件，改为"无增量输出的空闲时长"超时（例如默认 120s 无增量即失败）。长任务不再被砍，真挂死仍能被剪掉，且默认值可以更激进。

**成本/风险**：低。增量事件已有时间戳可用；需在 `TeamPorts` 上暴露最后活跃时刻。

### 2.3 重做注入携带尝试元数据

**现状**：Tier-1 恢复对在途节点按原模板重派（§6.5）。成员会话历史是持久的，崩溃重做后成员看到同一个任务的第二遍，却不知道上一次回答是被中断的残次品——可能回答"我已经做过了"，或基于自己的中断现场给出混乱输出。

**建议**：在 `team_context` 中附加 `attempt: <n>` 与"继续/重做"指令；重做时可附上次产出的尾部片段作为锚点。改动量约几行模板。

## 3. P1 —— 结构化输出契约与信息流

### 3.1 用工具调用替代 markdown 围栏 JSON

**现状**：Phase 1（条件分支）约定节点用 ` ```output ... ``` ` markdown 围栏块输出 JSON，条件表达式与循环终止条件都依赖解析它。该契约对小模型可靠性差：模型可能不按格式输出、围栏内混入注释、或整块遗漏——按 spec 设计，输出格式错误将导致 run `paused`，在多节点工作流中会频繁触发。

**建议**：节点可选绑定一个 `submit_result` function tool，模型通过工具调用提交结构化结果。校验失败的重试自然融入 agent 循环（工具回执错误 → 模型当轮自纠，与 `team_dispatch` 未知成员名的自纠机制同构），而不是整轮报废。顺带解决 `collect` 全文混杂寒暄/过程叙述的问题：**发布结果**（结构化）与**工作过程**（自然语言）分离，`{{节点}}` 模板注入可选择只引用结构化字段。

**依赖关系**：这是条件表达式、循环边条件求值、未来子工作流接口的共同地基，建议在 Phase 3 落地前先行。

### 3.2 协调者按需读取成员完整结果

**现状**：自动编排中协调者对成员产出的全部认知是 `_results_digest` 的每成员最新结果 **500 字符**，且多轮迭代被最新轮覆盖。成员可能干了很长的活（这正是 `reply_timeout` 被迫调大的原因），协调者却基于 500 字符做下一轮派发决策。

**建议**：给协调者增加 `team_read(member)` 工具，按需读取该成员本轮完整结果（从 `node_states`/`rounds` 中取）。按 `core/agent_team_tools.py` 现有的 per-umo registry 机制注册即可，不改变星型模型。`_results_digest` 可同步降为索引（成员名 + 一句话状态 + "可 team_read 查看全文"）。

### 3.3 受控的成员间结果直传

**现状**：星型拓扑下成员间信息只能绕经协调者（受 3.2 的瓶颈约束）或经 DAG 模板注入（仅限手动编排）。设计文档已把"成员间点对点自由消息"列为非目标，v1 不必推翻。

**建议**：折中方案——`team_dispatch` 的 assignment 支持 `inputs: [其他成员名]` 字段，由 runner 把被引用成员的（结构化）结果直接注入该成员的回合，成员自身不获得任何通信能力。信息不再绕经协调者窗口，星型安全模型不变。

## 4. P1 —— 可靠性与成本边界

### 4.1 run 级预算与 deadline

**现状**：只有 `max_rounds`（自动编排）和节点级 `reply_timeout`；没有 run 级总闸。10 成员 × 20 轮 × 长工具调用的 token/费用可能失控，且 DAG 模式连轮次上限都没有。

**建议**：团队 config 增加 `run_budget_tokens`（或费用近似）与 `run_deadline`；熔断时 run 转 `paused`（而非 `failed`），与现有失败策略语义衔接，用户可评估后恢复。

### 4.2 Tier 1.5：续聊恢复（可选能力）

**现状**：恢复语义是重做——在途节点重新派发一次新回合。dsh 的对比经验表明事件级对账成本很高，不必学；但 AstrBot 有一个被低估的资产：**成员会话历史天然持久**（`persist_user_history: True`）。

**建议**：对在途节点提供第二种恢复策略——向成员发"报告你当前进度并继续"的续聊回合，把已有工作捡回来。不需要任何对账基础设施，只是一次询问回合；对 600s 级长任务的重复成本改善明显。做成团队/节点级配置项（`redo` | `resume_chat`），默认维持 `redo`。

### 4.3 成员跨 run 记忆策略

**现状**：成员是长生命周期会话，同一团队第二次 run 时每个成员带着第一次 run 的全部历史。可能有益（连续性）也可能有害（上下文膨胀、旧结论污染新决策），目前是隐式行为。

**建议**：成员定义上增加记忆策略选项：每 run fork 全新对话 / 保留记忆 / 超过阈值后摘要压缩。与 conversation 服务的现有分支能力对齐。

## 5. P2 —— 配合既有 roadmap 的提醒

Phase 1-3 与 Subworkflow 落地时，建议一并考虑：

1. **干跑校验**：循环边 + 条件 + human input 组合后状态空间爆炸。保存/运行前增加静态可达性分析 + 迭代上限收紧检查，防止用户画出"永远停在 human_input"或"迭代上限形同虚设"的图。
2. **Subworkflow 恢复原子性**：现有"每转换即 UPDATE + 在途重做"在父子 run 嵌套时要定义清楚——子 run 重做时，父 run 视角下该节点处于什么状态；子 run `paused` 是否级联暂停父 run。
3. **golden run 录制/回放**：`build_ports_for_test` 已是现成的注入缝，延伸为录制真实 run 的 ports 调用序列、回放做回归测试，工作流模板即可带"已验证"属性。这也为模板库（roadmap 中）提供质量凭证。
4. **同成员波内去重**：同一成员绑定多个就绪节点时，`_wait_if_busy` 靠 2s 轮询串行化。调度层应保证同一成员同时只入一个在途节点（3.1 改为事件驱动后尤其容易做到）。

## 6. 与 dsh 实现的对照（背景参考）

| 维度 | AstrBot 现状 | dsh 做法 | 对本报告的启示 |
|---|---|---|---|
| 协作状态持久化 | 关系表 JSON 快照，逐转换 UPDATE | Lead 会话日志 event sourcing + 投影重放 | AstrBot 不必改；重做语义与之自洽 |
| 成员间通信 | 星型，非目标 | 任意成员间持久信箱 + Steer 投递 | §3.3 的受控直传是中间态 |
| 注入时机 | `is_busy` 2s 轮询忙等 | 步骤边界 steer / 空闲开轮 / 冷恢复 | 需 core 管道支持，v1 维持忙等 |
| 结构化输出 | （Phase 1 spec）markdown 围栏 JSON | 每工具声明完整输出 schema，编译器对齐 | §3.1 建议的直接依据 |
| 恢复 | Tier-1 重做 | 事件级对账（creation 核对、queued−delivered 重试） | §4.2 续聊恢复是低成本中间态 |
| 上下文与成员历史 | `mark_as_temp()` 不污染历史 | 团队消息是成员持久历史（带 source 去重） | 两者皆可；跨 run 记忆需显式策略（§4.3） |

## 7. 建议实施顺序

1. **第一批（P0，纯 runner 内部）**：2.1 事件驱动调度 → 2.2 空闲超时 → 2.3 重做元数据。互相独立，可单独出 PR。
2. **第二批（P1 地基）**：3.1 `submit_result` 工具化输出契约——为 Phase 3 循环边清障。
3. **第三批（P1 信息流与边界）**：3.2 `team_read` → 4.1 run 预算 → 3.3 受控直传。
4. **第四批（P2，随 roadmap）**：§5 各项在对应 Phase 落地时一并处理。

每条建议在实施前按仓库惯例出独立 design spec 并走设计评审。
