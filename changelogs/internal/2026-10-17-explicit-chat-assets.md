# Explicit chat asset invocation

- Add `/asset` for explicit team and workflow invocation, exact-name/ID selection, required-input clarification and root-run status/results. Ordinary chat keeps its existing behavior.
- Add **Workflow Assets → Chat access** to open a fixed version to a platform instance, sender, source conversation and source profile, or revoke that access. The grant also explicitly identifies the final-result delivery audience. It is local configuration and is excluded from portable packages.
- Reuse the existing asset, execution, human-request and run-detail services. Preserve the actual platform initiator; synthetic turns do not inherit Dashboard administrator roles. Recheck grants and source routing at external execution boundaries and before result release.
- Return acceptance, human-input notices and final results through persistent delivery cursors. Keep process, thinking, tools, child results and unapproved artifacts behind the existing Dashboard permissions.
- Entry mapping: chat callers previously needed the owner's **Workflow Assets → Start Run** action; they can now use an explicitly opened asset through `/asset`. Human requests continue at **Independent Runs → Run details → Human requests**. Incoming run links also select **Independent Runs** when the asset page is already open.
- Update the HTTP/OpenAPI contract, generated frontend client and English/Chinese instructions and screenshots. Notification transport remains subject to duplicate delivery if a process dies after the platform accepts a message but before its receipt is committed.
- Preserve the actual delivery audience: WeCom AI Bot asset replies bypass the global webhook and retain pending results after the original response expires. Background source delivery refuses adapter fallbacks that lose audience/account state. Satori and Misskey note sources cannot invoke or list opened assets until their source identity can distinguish those audiences; Misskey chats/rooms and source-addressed adapters remain available.
- Require an advertised original HTTP response stream before a WeCom asset command can create a run; webhook-only or empty-initial-response HTTP callbacks cannot invoke assets. Long-connection original-request replies remain available.
- Retain source notification receipts when QQ's cold session cache skips sending, and retry after the original scene becomes available. Propagate known Discord, Slack, Misskey and offline WebChat delivery refusals without changing ordinary chat's legacy Context return behavior.
- Let the real initiator confirm a short-lived browser connection from the original chat, view safe progress and answer the same persistent human request without a Dashboard account. Approval previews are scoped to the exact requested version; owner process, thinking, tools and unrelated artifacts remain private.
- Map chat-returned `/#/agent-teams?workflow_run=...` links to `/#/asset-run?workflow_run=...`. The original page remains the owner's full Dashboard view. Refresh, expiry or restart requires source confirmation again for the same run.
- Release a declined live response so a later background tick can retry through the same source, including an expired Discord interaction whose original channel remains available. Retain pending receipts when both channels are unavailable.
- Let confirmed chat initiators preview and download files declared by the root's exact completed result, including runs without an approval request. Preserve exact-version approvals and exclude private revisions, unrelated child files and other runs. Remove obsolete authorization screenshots while keeping the current bilingual steps.
