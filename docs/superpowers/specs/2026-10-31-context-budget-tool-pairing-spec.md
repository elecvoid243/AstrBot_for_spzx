# Coding Agent：增量上下文预算与工具调用配对

## 问题陈述

用户让 AstrBot 持续阅读代码、运行工具并修改项目时，一次用户请求通常会产生多次模型调用。当前上下文检查可以直接采用上次 Provider 返回的 token usage，但这个数值没有覆盖随后新增的工具结果、用户补充和上下文注入。因此，模型请求可能在本应压缩时仍被发送，最终因上下文超限而中断。没有可信 usage 时，单独估算消息也不足以覆盖工具定义等实际输入。

另一个问题发生在工具调用部分完成、取消、压缩或恢复之后。现有消息修复主要检查 assistant/tool 的排列，没有逐个核对 call_id。一条 assistant 消息同时调用 A、B，但只收到 A 的结果时，缺少 B 结果的请求仍可能进入 Provider，导致协议错误。错误关联工具结果还可能让模型误判操作是否成功。

这两类问题会导致长任务中断、重复读取、错误重试和进度判断失真。用户不应通过手动清空会话来规避它们。

## 解决方案

在现有 ToolLoopAgentRunner、ContextManager、ContextTruncator 和 Provider 调用流程内完成两项改进：

1. 每次模型调用前，根据实际准备发送的消息、工具定义和输出预算检查上下文。可信 usage 只作为与已知请求快照绑定的计数基准；新增内容增量计入，基准失效时重新估算。
2. 在模型可见的请求中，按 call_id 保证工具调用和结果完整、明确地对应。缺失结果使用真实的中断或未知状态补齐；孤立或歧义数据不能被当作成功结果发送。

复用现有压缩策略、工具执行和恢复机制。不增加用户操作步骤，不引入新依赖，不改变既有权限与工具重放授权规则。

## 用户故事

1. 作为 Coding Agent 用户，我希望新增的大型工具结果立即计入上下文预算，以便长任务在下一次模型请求前及时压缩。
2. 作为 Coding Agent 用户，我希望一批工具结果的累计体积被计入预算，以便多个分别不大的结果不会共同造成漏检。
3. 作为用户，我希望执行过程中补充的消息和系统注入也被计入预算，以便后续要求不会绕过请求检查。
4. 作为用户，我希望工具定义的大小被计入预算，以便启用较多插件时仍能合理管理上下文。
5. 作为用户，我希望连续多次检查不会重复累计相同消息，以便不会无故提前压缩并丢失细节。
6. 作为用户，我希望 Provider 未返回 usage 时仍能继续进行预算检查，以便兼容不同模型服务。
7. 作为用户，我希望缓存命中的输入仍计入上下文占用，以便缓存计费优惠不会被误认为上下文空间增加。
8. 作为用户，我希望压缩、历史截断和模型切换后重新确定有效预算，以便旧请求的 usage 不会污染新请求。
9. 作为用户，我希望恢复旧会话或检查点时不依赖缺少来源的 usage，以便恢复后的第一次请求也经过有效检查。
10. 作为用户，我希望输入为模型输出保留必要空间，以便请求不会因为输入占满窗口而失败。
11. 作为用户，我希望多工具调用只完成一部分时，模型仍能准确区分已完成与未获得结果的操作，以便任务可以正确继续。
12. 作为用户，我希望取消操作之后不会凭空出现成功结果，以便后续决策符合实际执行状态。
13. 作为用户，我希望输出顺序变化时仍按调用身份关联结果，以便不会把一个工具的输出当成另一个工具的输出。
14. 作为用户，我希望压缩或恢复后的工具调用仍满足模型协议，以便不因历史格式错误而中断。
15. 作为用户，我希望协议修复不会重新执行修改文件或其他有副作用的工具，以便避免重复修改。
16. 作为用户，我希望已经有效的消息及多模态结果不被无故改写，以便保留信息和缓存复用能力。
17. 作为维护者，我希望流式、非流式及工具参数补询路径遵循相同规则，以便修复不会只覆盖某一种调用方式。
18. 作为维护者，我希望测试通过实际送往 fake Provider 的请求验证行为，以便内部重构不会破坏测试价值。

## 实现决策

### 责任与现有接口

- ToolLoopAgentRunner 负责记录请求与响应的关联、选择有效的 Provider/model、汇入晚到消息，并在实际模型调用前执行最终检查。
- ContextManager 继续负责预算检查与既有压缩策略编排；ContextTruncator 的现有消息修复接口承担按 call_id 归一化的规则。
- TokenCounter 继续承担局部内容估算；不能由一个未关联请求快照的 trusted_token_usage 标量替代当前完整请求大小。内部调用方应明确区分估算值和具有有效来源的 usage 基准。
- 优先扩展现有接口，不新增独立的上下文框架、工具执行框架或 Provider 包装层。保留现有自定义 token counter 与 compressor 扩展能力，新增内部参数采用兼容的可选形式。
- 不新增 Dashboard 路由、公开请求/响应 schema、数据库表或用户配置开关。不修改插件仓库。

### 增量上下文预算

- 计数基准必须绑定成功完成的具体模型请求、有效 Provider/model，以及当时实际发送的消息和工具定义快照。只记录消息数量不足以识别同长度内容被改写的情况。
- 迁移 Codex 的“有效基准加新增内容”原则。AstrBot 的通用路径以该请求的 input usage 为基准，计入此后追加的实际模型消息、工具调用、工具结果和用户输入；避免直接将包含不可回传 reasoning 的总 output usage 当作下一次请求的实际输入。仍回传的 reasoning 内容按现有消息表示计入。
- input usage 包含 cached input。计费累计 usage、单次请求输入 usage 和下一次请求的预计上下文占用必须保持不同含义；不得把累计计费值作为窗口占用。
- 同一基准下重复检查、重试或恢复同一结果不能重复计入已经覆盖的内容。多个工具结果、额外用户内容和晚到的协作消息均须计入最终发送视图；同一内容不能因兼有消息表示和额外参数表示而计算两次。
- 无可靠 usage 时，估算当前完整的模型可见请求，包括 system 指令、消息及多模态内容、工具调用参数、实际提供的工具名称、描述和参数 schema。沿用现有估算能力，不引入精确 tokenizer 依赖，不把编码后的媒体字节直接当作文本 token。
- 历史压缩、截断、归一化造成的既有内容变化、system 指令变化、工具 schema 变化，以及 Provider/model 切换，均使不再匹配的基准失效；先重新估算，待对应的新请求成功后再建立基准。工具集合未变时不能重复增加 schema 开销。
- full、skills_like 及参数补询使用各自实际请求的工具 schema。压缩请求和参数补询返回的 usage 不得覆盖主循环中不匹配的基准。
- 只有完整、成功的响应才能建立新的可信基准。流式中间块、失败响应或本次缺失 usage 不得被当作新的可信快照；无法证明旧基准仍适用时回退完整估算。
- 恢复时只采用可以与恢复输入对应的基准。旧检查点或旧会话只有 usage 标量而无对应信息时，首次请求重新估算。无需为恢复基准进行数据库迁移；可靠恢复后的重新估算可以替代持久化基准。
- 保留现有绝对触发阈值和比例触发语义。已知窗口大小时，触发阈值还须服从输入加输出预算不超过窗口的约束；输出预算采用最终请求实际生效的 max_tokens 或 max_completion_tokens，包括既有执行预算对它的调整。没有显式输出上限时，沿用现有默认比例触发留下的余量，不猜测一个无限输出预算，也不新增配置旋钮。
- 完全禁用 token 限制时保留现有禁用语义；仅配置绝对阈值时继续按该阈值触发，不虚构模型窗口大小。
- 压缩完成后必须按新的消息和实际工具定义重新检查，不能继续沿用压缩前 usage。输出空间约束不满足且既有策略无法减小时，返回可理解的上下文容量错误，避免无限压缩、无限重试或继续发送已知超限请求。本项不要求实现当前长轮的细粒度压缩。
- 本地估算存在误差；该功能修复确定性的漏计和重复计数，不承诺消除所有 Provider 端的上下文限制错误。

### 工具调用与结果配对

- 只在工具调用批次已经结束、中断，或准备恢复历史并请求模型时归一化；不能因为一个工具还在运行就提前补上终态结果。
- 以 assistant 的工具调用批次为范围按 call_id 关联结果。不可按消息位置或工具名猜测，不可跨不相关批次借用同名 ID 的结果。合法的独立批次不因复用历史 ID 被错误合并。
- 每个有效调用在最终模型请求中有且只有一个对应的协议结果；一条 assistant 消息包含多个调用时逐个检查，不能因其中一个结果存在便认为整组完整。
- 保留已有真实结果的内容、错误状态、多模态内容及必要元数据。正常且合法的历史维持原有顺序；对于需要修复的乱序结果，在不跨越真实用户消息或其他调用批次的前提下整理为完整调用组。
- 缺失结果只能补充确定性的非成功说明。宿主明确知道调用已中断时说明中断；缺少权威执行证据时说明未收到结果、执行状态未知。不能声称工具执行成功，也不能声称未知操作一定没有执行。
- 没有对应调用的孤立结果从模型请求视图中排除；不能凭空生成一个工具调用使其看似合法。原始执行记录或检查点不得因此被删除。
- 完全相同的重复协议结果可以确定性去重；冲突的重复结果、同一批次的重复调用 ID、缺少必要 ID 等无法无歧义关联的数据，应阻止该请求并报告协议完整性错误，不能任意挑选成功结果或静默丢弃调用。
- 工具执行器通过多次 yield 返回内容是既有行为，不等同于重试产生的重复结果。属于同一次调用的已知多段输出应按原有顺序汇聚成一个协议结果，保留文本及多模态内容；不得简单只保留第一段或最后一段。无法安全汇聚时使用明确错误，不发送含糊的多重结果。
- 归一化必须幂等：同一输入多次处理不会追加多个占位结果，不生成随机标识或时间戳，不改变本已有效的消息内容。
- 占位内容属于模型输入修复，不是 ToolRecovery 的权威执行证据；不得把调用记录从 unknown/started 改成 succeeded、failed 或 not_executed，不得标记真实结果已经持久化，不得触发工具重放。原有阻止不安全恢复的条件保持有效。
- 归一化无法可靠完成时，错误必须传播到调用者并阻止 Provider 请求，不能被压缩管理器的宽泛异常回退吞掉后发送原始无效历史。

### 请求时序与覆盖范围

- 在实际 Provider 调用前，基于最终有效消息进行模态适配、配对检查和预算检查。检查后的新增消息、工具定义替换或模型切换必须使相应检查重新生效；检查点与缓存指纹对应实际发送的同一请求视图。
- 需要压缩时，传给摘要 Provider 的历史也必须有合法配对。压缩得到替换历史之后，再检查配对和预算。
- 覆盖 ToolLoopAgentRunner 的普通请求、流式请求、fallback/retry、最终收尾请求和 skills_like 参数补询；复用内核压缩器的摘要请求遵循相同的协议规则。
- 对子 agent、定时任务或协作任务，只覆盖其使用上述现有 Runner 的路径；不扩展到第三方托管 Agent 内部，不新增其执行恢复能力。

## 测试决策

### 主验收 seam

使用现有 ToolLoopAgentRunner 驱动入口作为唯一主验收 seam，注入可记录请求并返回预设响应的 fake Provider，以及可记录调用次数、顺序、取消和副作用次数的 fake ToolExecutor。通过真实 Runner、ContextManager、计数与归一化逻辑，断言最终 Provider 输入、用户可观察的压缩/失败事件和工具执行次数。

不新增生产 seam。对于组合数量较多的消息配对边界，补充现有 ContextTruncator 公共修复接口的表驱动测试；它是已有 seam，不替代主链路验收。

### 行为验收

| 场景 | 必须满足的外部行为 |
| --- | --- |
| usage 尚未到触发线，新增工具结果越线 | 下一次普通模型请求前发生压缩或明确容量拒绝，不能沿用旧 usage 绕过检查 |
| 多个工具结果累计越线 | 按总增量触发；不是只计算最后一个结果 |
| 同一输入重复检查或请求重试 | 不重复计数，不新增无故压缩，不重复执行工具 |
| 一段工具结果恰好跨越触发条件 | 测试使用已知内容和受控 usage 验证阈值上下两侧，避免依赖真实模型 tokenizer |
| Provider 缺失 usage，或 cached input 很大 | 前者完整估算，后者包含缓存输入；不能把缓存 token 从窗口占用中扣除 |
| system、工具 schema 或既有消息原位修改 | 旧基准失效，按实际新请求估算；消息数量不变也能覆盖 |
| 压缩、按轮截断、Provider/model 切换 | 重新计数并采用目标模型窗口；不沿用旧快照 |
| skills_like 参数补询和摘要调用 | 各自按实际消息与 schema 检查，不污染主请求基准 |
| 晚到的用户/协作消息、最终收尾提示 | 真正发送前也被纳入配对及预算检查 |
| 输出预算使当前请求无法容纳 | 先使用现有压缩策略，仍无法满足时明确失败且不调用普通 Provider，不无限重试 |
| 无窗口限制或仅有绝对阈值 | 分别保持禁用语义与绝对阈值语义 |
| A、B 两个调用只有 A 返回 | A 的真实结果保留；B 获得中断或未知说明；请求配对完整 |
| A、B 的结果逆序返回 | 仍按各自 call_id 匹配，内容不串线 |
| 全部结果缺失或只存在孤立结果 | 合法调用获得非成功占位；孤立结果不进入请求；原始记录不被抹除 |
| 合法重复 yield 与重复协议记录 | 前者有序汇聚，后者仅在完全相同时去重，不丢失有效内容 |
| 冲突结果、批次内重复 ID、无 ID | 明确协议错误，Provider 调用次数为零，不任意猜测 |
| 同 ID 出现在不同已闭合批次 | 保持批次关联，不串用历史结果 |
| 归一化再次处理同一请求 | 消息内容和标识稳定，无额外占位 |
| 工具中断后继续或恢复 | 不把未知结果改成成功，不因协议修复重复执行有副作用的工具 |
| 流式取消和旧检查点恢复 | 不从未完成响应建立可信 usage；旧快照安全退化为重新估算 |
| 正常历史与多模态结果 | 内容、错误状态及媒体保留，合法请求不被无故改写 |
| 预算与配对同时需要修复 | 先得到合法模型视图再计入包括占位在内的最终输入，压缩后的请求仍满足两项约束 |

### 测试原则与先例

- 不通过 mock should_compress 的返回值证明预算正确，不断言私有缓存字段或辅助函数调用次数；使用可控制的请求与响应证明结果。
- 复用已有 Runner 的 MockProvider、usage 变化、工具结果刷新、停止取消和多模态工具测试先例。
- 复用已有 ContextManager 的压缩阈值、压缩失败回退、自定义 compressor 与近期历史保留测试先例。
- 恢复行为复用已有工具调用检查点和权限恢复测试，重点断言真实工具执行次数与 unknown 状态保持。
- 核心验收不访问真实模型或网络，不依赖外部凭证。流式与非流式复用同一行为场景，避免复制整套断言。
- 实现交付时运行受影响测试及仓库要求的 Ruff 格式化和检查；本 spec 不包含实现代码，也不以运行现有测试代替新行为验收。

## 范围外

- 首尾输出截断、输出预算在工具之间的动态分配和输出存储改造。
- 当前长轮的细粒度压缩、摘要提示词重写、长期记忆和检索。
- 工具按需发现、工具并发调度、Shell/PTY、沙箱与权限策略改造。
- AGENTS 指令发现、插件功能本体化和新的用户界面。
- 新的数据库迁移、普通会话持久恢复体系、第三方 Agent 的内部请求管理。
- 精确 tokenizer、跨 Provider 的计费重构，以及改变工具幂等性或重放授权。
- 将 Codex 的 Rust 运行时或 OpenAI 专用协议整体移植到 AstrBot。

## 进一步说明

- 本规范合并此前建议中的第 1 项与第 2 项，因为两者都约束实际发送给 Provider 的上下文，主验收 seam 可以共用。它不授权实施此前第 3 至第 8 项。
- Codex 的参考价值在于 usage 基准加增量、完整 call/output 配对、稳定的修复结果，以及明确区分模型窗口和执行事实。AstrBot 保留自己的 Python 实现、多 Provider 兼容和更严格的工具恢复契约。
- 与现有 [插件功能本体化规范 #72](https://github.com/elecvoid243/AstrBot_for_spzx/issues/72) 协调：复用内核压缩规则，不重新实现 compact 插件迁移或新增一套手动压缩配置。
- 用户主动取消必须继续优先停止任务；协议修复不能成为取消后继续调用模型或工具的理由。后续请求或已经获准恢复时，再构造合法模型输入。
- 发布到项目 Issue 跟踪器时仅应用 ready-for-agent 标签。
